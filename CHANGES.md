## Release Notes

**Unreleased**

- **FIXED:** Craft sync now repairs a stale document ID that Craft no longer knows. A structured `GET /blocks` 404 on an index document, or a link-row `POST /blocks` 404, creates a fresh replacement document and records it in `craft_links` immediately - **before** any further API call - so a failure in the rest of the repair leaves a tracked replacement rather than an orphan, and the next run resumes from it. Recovery **never adopts** a same-title document: a title match is not proof of ownership, and the index writer would then delete an unrelated user page's content wholesale. First-sync adoption, where `craft_links` records no document ID at all, is unchanged. One run replaces at most `_MAX_DOCUMENT_REPAIRS_PER_RUN` (10) stale IDs before it aborts with a `CraftApiError`: past that the 404s are a dead or misdirected connection, not isolated drift, and must fail loudly rather than create one document per entity on every run. A structured `DELETE /blocks` 404 on a tracked link-row block is logged and treated as already-deleted; `_write_index_content`'s own bulk delete is deliberately not wrapped, so its 404s still surface. `classify_failure` now checks the error message for an auth failure **before** classing a structured 404 as `not-found`, because a revoked Craft connection returns 404 for every path and `not-found` reads to the user as "just retry". A repaired-ID count is reported as `documents_repaired` in the sync summary, and each replacement is logged. `CraftApiError` carries structured `method`, `path`, `statusCode` and `responseText` fields; `db.upsert_craft_link` gains a `clearUrl` flag for the case where a replacement has no resolvable deep link.
- **FEATURE:** the Alfred workflow's mutating half, slice 2 of the specification: `add_id` end to end, plus the machinery every other mutating command will reuse. A command row now sits below the entities in the one `av` list - they share it because "Alfred Filters Results" runs the Script Filter once with an empty query, so there is no second pass to add rows in - and ↩ on it starts a five-step flow: category pick, one `title, description` field split on the first comma, a confirmation screen, the run, and a success surface built from the new entity's own record. The confirmation is the commit: the argument step's final ↩ only reaches it, **Create as typed** is its first and default row, and accepting a spelling correction re-renders the screen rather than creating anything, so ↩ always means create. Teaching the learned vocabulary is **⌘↩ on a correction row**, a deliberate divergence from the terminal, where declining a suggestion teaches the word - under this shape declining is the default path, so the terminal's rule would teach a word on every reflexive Return. The success surface exists because the Script Filter's index is cached for an hour: a brand-new folder appears in the list one invocation late at worst, and this reaches it immediately.
- **FEATURE:** `--json` on `add_id`, returning the uniform mutating result the contract defines - `action`, the new `entity` record, `corrections`, `suggestions`, `sync` and `warnings`. **`corrections` and `suggestions` are not synonyms**: the first is what was substituted into the title, the second what was offered and not accepted. A headless run prompts about nothing and so applies nothing, which is exactly the run Alfred needs the offers for, so detection now runs whether or not anything is asked. New `spell_check.detect` reports suspect tokens without prompting, `spell_check.substituted_title` accepts one without prompting, and `spell_check.checked_title_details` returns the title with both fields. **`--json` now says it will not prompt rather than inferring it from `isatty`** - the inference held for Alfred, whose subprocess has no terminal, and blocked forever for anyone running `aardvark add_id … --json` from a real shell. `add_id.get()` returns `(code, folderPath, details)`, reporting the whole outcome through the return rather than leaving half of it on the worker to be read afterwards. `_hand_off_sync` now reports which of `backgrounded`, `waited` or `none` actually happened.
- **ENHANCEMENT:** retune the title spell-checker, measured on 141 real human-typed titles. `suggest` now prefers the **longest** distance-1 candidate rather than the shortest, which takes right offers from 57.6 to 75.0 per cent and wrong offers from 25.0 to 7.6 per cent at no cost to how often the check fires - a dropped letter is the commonest typo and leaves the token shorter than its correction, so the old rule picked against the commonest case by construction, and `setings` now offers `settings` rather than `stings`. `MINIMUM_TOKEN_LENGTH` moves from 6 to 5, taking dropped-letter recall from 61.0 to 87.8 per cent and the silent rate from 17.4 to 5.4 per cent: dropping a letter from a six-character word leaves five, so `sysem`, `famil` and `acive` were previously never checked at all. The cost is four more suspect tokens across those 141 titles, all proper nouns the learned vocabulary retires at one dismissal each, for a per-title fire rate of 4.3 per cent against a stated ceiling of 5. A floor of 4 is rejected on its own numbers - the same recall, and 12.8 per cent of titles firing. No wordlist change, and the module docstring's unqualified "18 per cent" is replaced by all three rates with their denominators.
- **FEATURE:** the Alfred workflow itself, slice 1 of the specification below. `aardvark install_alfred` does two separable jobs: it always records this Mac's `aardvark` console-script path in a one-line file at `~/.config/aardvark/alfred-binary-path`, and it symlinks the packaged workflow at `aardvark_jd/resources/alfred/` into Alfred's `workflows/aardvark-jd`. Symlink only, no copy mode - `importlib.resources` resolves to the working tree for an editable install and to site-packages for a package user through one code path, so the author gets live editing and everyone else gets a workflow that `pip install --upgrade` refreshes. Re-running is idempotent across all four target states and an imported `.alfredworkflow` directory is never touched; `--uninstall` removes the symlink and the pointer and nothing else. Alfred's location comes from its own `prefs.json` and **never** from a default path, because `~/Library/Application Support/Alfred/Alfred.alfredpreferences` exists on some machines but is vestigial, so a fallback would write where Alfred never looks and appear to succeed. The workflow itself is one `av` Script Filter over the whole index, with ↩ opening every synced mirror, ⌘ revealing in Finder, ⌥ opening a terminal tab and ⌃ showing the four mirrors as rows that offer to sync whichever are missing. The binary resolution - configuration variable, then pointer, then a row saying so - lives in `aardvark_jd/alfred/binary.py` and is replicated in the workflow's own `_resolve.sh`, which cannot import it because resolving the binary is what lets the workflow run Python at all. `make alfred-normalise` sorts `info.plist`'s `objects` array by `uid`, which is the only churn Alfred's editor produces that is worth containing.
- **FEATURE:** a `--json` flag on `fd` and `open`, plus `--archived` on `fd`, printing a versioned machine-readable object instead of prose. The envelope carries a `system` block and a **flat** `entities` array in index order, each record holding its Johnny Decimal code, title, description, emoji, folder path and every mirror URL - Finder, Craft, Todoist, Drive and Dropbox - with `null` for a mirror not yet synced. `open --json` opens nothing, never falls back to the interactive picker, and treats an entity synced to nothing as a result rather than an error. Both failure exits fork on the flag, writing `{"error": {"kind", "message"}}` to stdout with a non-zero exit, since Alfred reads stdout regardless of the exit code; `kind` is a stable machine token. The mirror URLs come from one new bulk read, `db.entities_with_links`, rather than the four per-entity link lookups `open` uses, and the rendering lives in a new pure `aardvark_jd/json_output.py`. **The contract is internal and unstable**: nothing outside this repository may depend on it, and its `aardvark_json` integer is bumped on any breaking change.

- **FEATURE:** `add_area`, `add_category`, `add_id` and `add_project` offer to correct a suspected typo in a new title, **before** anything is created. Checking first is what designs the hard case out: the corrected title is the single value the folder name, the index row and all three mirrors are built from, so there is no post-creation rename and no mirror repoint. The check *offers* and never blocks or silently rewrites, which is arithmetic rather than politeness - on a realistic technical vocabulary this configuration flags **18 per cent** of tokens (`jupyter` to `jupiter`, `pydantic` to `pedantic`, `postgres` to `postures`), so a checker that corrected without asking would corrupt titles routinely. Two rules keep that rate down and matter far more than the choice of wordlist: only tokens of **six characters or more** are checked, and a correction is offered only when a **distance-1 dictionary word actually exists**. Distance 2 was measured and rejected at 49 per cent false positives and 850 times the runtime. Interactive runs get one `[y/N]` prompt per suspect token, ahead of the emoji prompt because accepting changes the title the emoji is derived from; non-interactive runs create the entity exactly as typed and print one note per suspect token to stderr, never blocking. A new `spell_check.enabled` setting (default `true`) switches the whole thing off.

- **FEATURE:** declining a suggestion records that word in **`<root>/.aardvark-vocabulary`**, permanently, and it is never offered again - so the low-friction answer (`N`, or a bare Enter) is the one that makes the feature go quiet on your own jargon as you use it. That self-silencing is what makes an 18 per cent false-positive rate tolerable, and it is the reason the feature is worth shipping at all. The file is a sorted, newline-delimited, hand-editable dotfile written atomically on each dismissal, created lazily on the first one, and it sits at the system root *outside* `00_INDEX🗂️` so it syncs between machines rather than being caught by the index's Dropbox exclusion: it records **this user's** jargon, not any one machine's. It starts empty and is never seeded from the existing tree, so live typos already in the tree stay catchable. Every read and write degrades with a warning rather than raising - a spell-check helper must never be able to break `av add_project`.

- **FEATURE:** ships the ESDB/SCOWL `en_GB-ise` size-60 British English word list (87,851 words) in `aardvark_jd/resources/wordlists/`, with its copyright notice alongside and an attribution in `LICENSE`. It is a plain list read into a `frozenset` (**10.6 ms**, measured) rather than a spell-checking library, because `spylls` costs 402 ms to load and `symspellpy` 1,212 ms to index - both fatal against the 500 ms command budget. The load is lazy, so a command with no token worth checking never pays it; a whole `av add_area` with the check in measures **226 ms**. No new dependency.
- **FEATURE:** the seven mutating commands (`add_area`, `add_category`, `add_id`, `add_project`, `set_emoji`, `repair_emoji`, `archive`) no longer wait for the remote mirrors. They do their local work, hand the sync to a detached `aardvark craft_sync` - which already runs `gdrive -> todoist -> craft` in the mandated order, so it is one spawn and no new sync code path - and exit. Measurement put `av add_project` at **30.7 s against a 500 ms target**, 29.9 s of it network across four services in a fixed sequence, and no call-count optimisation reaches that target while the command waits. The gate survives restated as **local work plus handoff**. Recorded as [ADR 0001](docs/adr/0001-mutating-commands-hand-sync-to-a-detached-process.md). The explicit `*_sync` and `connect_*` commands stay in the foreground - a first backfill is the run most likely to be rate-limited and the worst possible one to hide - and a new **`-w`/`--wait`** forces the foreground path on any mutating command, exiting non-zero if a mirror failed. That non-zero does not mean the command failed: the folder, the index row and the Johnny Decimal code all exist; it means the entity was created and a mirror did not sync.

- **FEATURE:** at most one sync runs at a time, held by a lockfile beside `aardvark.db` inside the (Dropbox-ignored, so per-machine) `00_INDEX🗂️` directory, carrying a pid and a start time. A mutation arriving mid-sync sets a **pending flag** rather than starting a second writer, and the running sync re-checks it on completion and goes round again - not a queue, because a whole-tree repair subsumes every mutation made during the previous run, so one slot is enough and the loop drains as soon as the user stops typing. This is what lets the concurrency contract stand unchanged and WAL stay declined. A stale lock would stop syncing silently and permanently, so a lock whose pid is gone is taken over, with an age cutoff as a backstop against pid reuse - **derived from** `http_retry`'s per-run backoff budget rather than picked separately, since it must exceed the longest legitimate run. A run that **abandons** on budget exhaustion clears the pending flag instead of looping, closing a hot loop in which a rate-limited sync would restart itself forever in a process nobody is watching.

- **FEATURE:** per-mirror **drift markers**. The process that would have reported a sync failure has exited, so each mirror's outcome is recorded in a new `sync_drift` table (schema v6) with its last success, last failure, and a reason **class** - `rate-limited`, `auth`, `network` or `unknown` - because "craft is rate limited" resolves itself and "craft's token expired" never will, and those need opposite responses. Per-mirror rather than per-system because partial failure is real: the three run in sequence, so Drive can succeed while craft is rate-limited. `aardvark search` heads its listing with any drifted mirror, and the next command prints a one-line warning - relying on the listing alone would leave a failed sync invisible until the user happened to run it. A mirror's marker is cleared by its next success.

- **ENHANCEMENT:** the three mirrors of one invocation share a single retry/backoff budget, so a command's total backoff is bounded however many mirrors it runs - which is what the stale-lock cutoff is derived from, since per-mirror budgets would put a legitimate run's worst case at three times that cutoff's own basis and a healthy-but-throttled sync could have its lock stolen mid-flight. Retries are announced to stderr only when stderr is a terminal; the detached carrier's stderr is `/dev/null`, and `http_retry` routes each message to the announcer *or* the log, so announcing unconditionally would have thrown the background run's retry detail away entirely.

- **FEATURE:** the aardvark index directory is excluded from Dropbox sync. The index database lives at `<root>/00_INDEX🗂️/aardvark.db` inside the Dropbox-synced tree, and Dropbox syncing a SQLite database between machines risks corruption - more so once a write-ahead log exists, whose `-wal`/`-shm` sidecars are uploaded even when the database itself is excluded. A new `dropbox_ignore` module sets Dropbox's `com.dropbox.ignored` extended attribute on the `00_INDEX🗂️` directory, via a `ctypes` libc `setxattr` call (CPython has no `os.setxattr` on macOS, and this avoids both a new dependency and a `/usr/bin/xattr` subprocess per command). It is applied at `aardvark init` and re-asserted idempotently before every non-completion command opens the database, so a second machine that clones the Dropbox tree excludes the index on its first `aardvark` run. Setting the attribute on an already-synced directory makes the Dropbox client purge the server-side copy on its own, so there is no API delete step. The mechanism is a no-op unless the system root is inside a local Dropbox tree, and outside macOS it logs one warning and does nothing (the Linux and Windows equivalents are deferred until a second platform runs aardvark). **This changes today's behaviour: the live `aardvark.db` currently syncs to Dropbox and will stop, and be removed from Dropbox's servers, on the next `aardvark` command.** WAL itself stays disabled (see the concurrency note below).

- **FEATURE:** shared retry, backoff and timeout policy for the mirror HTTP clients, in a new `http_retry` module. Every request the craft, Google Drive and Todoist clients make now carries a `(5s connect, 30s read)` timeout - without which a hung connection in a detached sync would hold the sync lock forever - and is retried on `429`, `5xx`, connection errors and timeouts, plus a `403` whose body reason is one of Drive's rate-limit reasons (`userRateLimitExceeded` / `rateLimitExceeded`), because Drive signals throttling with a `403` rather than a `429`. A plain `403` is never retried. Backoff is truncated exponential with jitter, honouring `Retry-After`, and every sleep is charged against a per-run `RunBudget` (5 minutes) so a rate-limited run abandons after a bounded total rather than the sum of every request's worst case. Response headers are logged at `WARNING` on any `429` or rate-limit `403`, so craft's undocumented limit is captured the next time it is hit. The Dropbox client gets the timeout but not the retry loop - it makes at most a handful of best-effort calls per run.
- **FIXED:** `_write_index_content` inserts an index document's new body before deleting the old one, not after. Craft has no atomic replace, and a rate limit landing between the two calls previously left the document silently empty; insert-then-delete leaves it briefly holding both, which the next whole-tree repair reconciles.
- **FIXED:** when every link source for an index document becomes unavailable (off Darwin, no Dropbox/Drive/Todoist link), `_write_link_row` now clears the recorded `links_markdown` and deletes any stale link-row block, instead of returning and leaving `_write_index_content` to compare forever against a link row the document no longer has and rewrite it on every run. `db.upsert_craft_link` gains a `clearLinksMarkdown` flag, mirroring `clearBlockId`.
- **ENHANCEMENT:** `gdrive_sync` lists the existing Drive tree one `files.list` per depth level instead of one per interior folder. `gdrive_client.list_child_folders_multi` ORs up to 50 parents into a single query, and a breadth-first prefetch at the start of the run fills the child index for the whole subtree - taking the 163-folder aardvark tree from ~45 listings to ~5. The old walk scaled with the shape of the tree, so every new category added a call to every future run. Drive's published quotas were never close (~1.4 per cent), so this is a latency change, not a rate-limit one; the corrected `list_child_folders` docstring no longer claims Drive has no cheap whole-tree listing. HTTP batching was rejected - Google counts a batch of *n* as *n* requests, so it is strictly dominated by the OR-ed query.
- **ENHANCEMENT:** `db.get_connection` and the read-only shell-completion connection both set `PRAGMA busy_timeout = 5000` explicitly, so a command or a TAB press waits out a concurrent write rather than failing immediately. The Python 3.14 stdlib already defaults this, but aardvark's concurrency contract now depends on it. WAL is deliberately not enabled: the `mode=ro` completion reader depends on the `delete` journal-mode default.

- **FIXED:** `craft_sync` no longer rewrites every index document on every run, which is what exhausted craft.do's rate limit. `_write_index_content` now reads the existing content, compares it against the computed listing and returns without writing when they match, and the forced link-row rewrite that followed it is skipped with it - the two are coupled, because only a real content rewrite invalidates the link row's recorded block id. Measured against the live space: `av add_project` fell from 118 craft calls to 41, an unchanged repair run from 101 calls (which died on a `429`) to **30, every one a read**, and no 429 has recurred. The comparison is exact over the document's whole content - the link row `_write_link_row` last recorded (or nothing, where no Finder/Dropbox/Drive/Todoist link is available) followed by the computed body - so a removed entry still listed, a hand-added note or a hand-deleted link row all fail the match and force the drift-repairing rewrite. It `rstrip`s both sides because Craft strips trailing whitespace when it stores a block - without which any entry with an empty description, meaning every project, would never compare equal and would rewrite forever. `FakeCraftClient` was corrected to match the real API it stands in for: one block per line, `position="start"` actually prepending, and trailing whitespace stripped.

Seeded while wayfinding the remote-sync execution model.
- **FEATURE:** tab completion for `bash` and `zsh`, installed with `eval "$(aardvark completion zsh)"` (or `completion bash`) in your shell's rc file. Subcommands complete by name, and `<domainLetter>`, `<area>`, `<category>` and `<ref>` complete from the live SQLite index - so `aardvark archive A11.<TAB>` offers exactly the IDs that exist. The shells call a hidden `__complete` subcommand, intercepted before docopt (which would reject an undeclared command) and before `fundamentals.tools`, so a keystroke never pays for settings-file creation, logging setup or a schema migration; the index is opened read-only, an explicit `-s` on the line being typed is honoured, and every failure is swallowed silently rather than spilling a traceback into the completion buffer.
- **FEATURE:** new `archive <ref>` command, retiring an area, category or ID and **freeing its Johnny Decimal number for reuse**. The folder moves into the nearest reserved `09_archive🗄️` - a category's own for an ID, the parent area's system folder for a category, the domain's for an area - which is the first thing ever to write into that scaffolding. The row leaves `areas`/`categories`/`ids` for a new `archived_entities` table rather than being flagged in place: the live tables carry `UNIQUE (domain, ac_number[, item_number])`, so a row cannot both stay put and surrender its number, and - more importantly - all three sync engines adopt-or-create *by name*, so one query that forgot an `archived` filter would silently rebuild the archived structure on the next sync. Removing the row makes that whole class of bug impossible and evicts it from the search index for free. Archived folders are datestamped (`A11.10_cardiologist__archived_20260820`), which is load-bearing rather than decorative: once a number is reused, the next entity to be archived would otherwise collide with the first. Destructive and one-way - there is no `unarchive` - so it confirms interactively unless given `-y`.
- **FEATURE:** new `connect_gdrive <clientId> <clientSecret>` and `gdrive_sync` commands, mirroring the folder tree into Google Drive - **folders only, never documents**.
